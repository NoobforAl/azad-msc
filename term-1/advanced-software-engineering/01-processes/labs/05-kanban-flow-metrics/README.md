# Lab 01.5 — Kanban flow metrics: cycle time, throughput, WIP and Little's law

**Goal:** compute cycle time, lead time, throughput and work in progress from a small issue export, and show with two simulated teams why limiting work in progress shortens cycle time without reducing throughput.

Runs on: Python >= 3.8 (stdlib only). Time: 45 min. Difficulty: medium.

## Starting state

- Module state `m0`: no project files are needed. The "issues" are the work items of a team building the Course Registration Platform, **generated by a simulation** (see below). They are synthetic, not data from a real team.
- Ending state: `gen_issues.py` and `flow_metrics.py`, plus two CSV exports; they join `m1` as `tools/` (see [`../README.md`](../README.md)).

## Background

Kanban manages flow with a visible board and a **work-in-progress (WIP) limit**. Schach 8e does not mention Kanban (we searched the book's text); his agile coverage is ch. 2 §2.9.5, which mentions timeboxing and stand-up meetings, see module 01 note 06. The metrics:

| Metric | Definition used here |
|---|---|
| Cycle time | days from "started" to "done" (inclusive, calendar days) |
| Lead time | days from "created" to "done" (what the requester feels) |
| Throughput | issues finished per week |
| WIP | issues started and not finished, counted on each working day |
| Aging WIP | days since start of an issue that is still open |

**Little's law:** for a stable system the average WIP equals throughput times average cycle time (L = lambda x W). It is a mathematical identity for a system in steady state, not a management trick; it says that at constant throughput, *less WIP means shorter cycle time*. (Little, 1961, is the usual source; not opened for this lab, `UNVERIFIED`.)

How the synthetic data are made (`gen_issues.py`, all numbers are assumptions): 3 developers give 3 developer-days per working day (Monday to Friday); each working day a new issue arrives with probability 0.85; an issue needs 1, 1, 2, 2, 2, 3, 3, 4, 5 or 8 developer-days (drawn at random, mean 3.1); one developer works at most one day per day on one issue. The two exports use the **same arrivals and efforts**; only the policy differs:

- `issues-nolimit.csv`: everything is started the day it arrives and the three developer-days are shared round-robin among everything in progress (multitasking).
- `issues-wip3.csv`: an issue is started only if fewer than 3 are in progress (oldest first).

The random numbers come from a tiny linear congruential generator, so the files are identical on every machine and can be regenerated.

## What to observe

1. **Same throughput, much shorter cycle time.** 4.25 vs 4.33 issues per week, but the mean cycle time falls from 9.9 to 3.9 days and the 85th percentile from 18 to 6. The p85 is what you would promise a stakeholder ("85% of issues finish within 6 days"), which a mean hides. The worst case falls from 41 days to 12.
2. **Lead time falls less than cycle time.** The limited team's lead time is 8.9 days, because issues now wait in the backlog instead of being "in progress" while nobody works on them. The queue did not vanish; it became visible and honest.
3. **Little's law holds.** Throughput x cycle time (in working days) is within 5% of the measured WIP in both runs (6.28 vs 6.55 and 2.78 vs 2.83); the gap comes from the window edges (issues open at the start or end). Halving WIP at the same throughput halves cycle time: the arithmetic is the whole argument.
4. **A limit below capacity costs throughput.** Limits 1 and 2 starve the team (1.33 and 2.50 issues per week); limit 3 matches three developers; limits above 3 only add waiting. In this model the best limit equals the team size, which is a property of the model (one developer per issue), not a general rule (`OPINION / CONTESTED` for real teams; pairing, specialists and blocked work change it).
5. **Aging WIP is the early warning.** The `nolimit` run still has issues open for 8 and 9 days at the end; a cycle-time mean only moves after they finish.

## Pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| cycle time is 1 for items done in a day, not 0 | durations are inclusive by design | subtract 1 if your tool counts differences |
| weekend days inflate cycle time | durations are calendar days | count working days (see `working_days` in the code) if your team does not work weekends |
| throughput looks lumpy (2, 3, 4, 8) | a week is a small sample | use a 4-week rolling mean before drawing conclusions |
| Little's law is off by more than 10% | the window is short, or the system is not stable (WIP grows all the time) | measure over more weeks, or check that WIP does not trend upward |
| `ValueError: Invalid isoformat string` | the CSV has another date format | export ISO dates `YYYY-MM-DD` |
| comparing the two reports gives different issue counts | one run had issues still open, started or not at the end | use the same `--as-of` date for both |
